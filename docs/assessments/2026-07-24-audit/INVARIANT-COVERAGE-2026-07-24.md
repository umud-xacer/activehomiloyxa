# Invariant coverage — I-01…I-24 (P-AUDIT, 2026-07-24)

Source of the exact invariant statements: `docs/Active-Home-Domain-Model-v1.0.docx`, Section 9 ("Consistency Rules (Invariants)"), extracted directly for this audit (not paraphrased from memory).

**Important caveat, established during this audit (see the full report's Section C):** the codebase's `test_I<nn>_*` naming convention is *not* a reliable 1:1 pointer to these global ids. The same numeric pattern is independently reused by: each module's own `test_boundary_import.py` (a local "I-01..I-06" sequence about import-linter contracts), `backbone`'s own infra-invariant tests (a local "I-09..I-17" sequence about outbox atomicity / schema roles / migration safety / logging redaction), `shared_kernel`'s own VO-equality tests, and `search`'s internal cross-script-matching tests (a local "I-08..I-16+" sequence). Every row below was verified by **reading the test's actual assertion content** and confirming it matches the Domain Model's exact wording, in the module the Domain Model's own "Scope" column assigns it to — not by grepping for a matching number.

## Summary

**24 / 24 invariants have real, content-verified, currently-passing test coverage.** None are ABSENT. This is the single most positive finding of this audit, with one important qualifier stated above and in the full report: roughly half of these are covered by tests that are **not** literally named `test_I<nn>_*` after their true global id — the coverage is real, but a naive `grep`-based traceability check (the kind an automated tool or a future contributor might rely on) would significantly undercount or misattribute it. This naming-convention inconsistency is tracked as Gap Backlog item **G-022** (MINOR — tooling/process debt, not a functional defect).
